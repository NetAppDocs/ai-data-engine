= AI Data Engine requirements
:icons: font
:imagesdir: ../media/

[.lead]
Before you deploy AI Data Engine, review the networking, Kubernetes, sizing, and operating system requirements for your environment. For a single-node deployment, you provide a Linux VM and AI Data Engine provisions everything else automatically. For a multi-node deployment, you bring your own Kubernetes cluster.

[[flexible-sizing-single-node]]
=== Flexible sizing guidelines

<<single-node-vm-sizes,Small, Medium, and Large configurations>> are recommended baselines for a three to four day initial scan window, not hard limits enforced by the software.

What drives the sizing recommendations::
+
* *Total file and directory count*: The total number of objects to catalog is the dominant driver of compute and storage requirements. Higher object counts require proportionally more memory, CPU, and storage.
* *Directory structure*: Resource use varies with directory nesting depth and how files are distributed across shares and volumes. Deeply nested or highly fragmented structures can require more resources than the same file count in a flatter hierarchy.
* *Required scan throughput*: Initial catalog completion speed is tied directly to CPU and memory allocation. Provisioning below the recommended size reduces throughput and extends the initial scan window.
* *Storage performance*: High-performance storage is strongly recommended. Metadata indexing and event processing require sustained IOPS and throughput proportional to the deployment size.

What happens if you undersize or outgrow the deployed size::
+
Each configuration is tuned for a specific file count and scan rate. If your environment exceeds what the configuration supports, you can expect the following:
+
* *Extended initial catalog duration*: Reduced compute lowers objects scanned per day. For example, a deployment targeting 3 billion objects but provisioned at a smaller size can take significantly longer than the three to four day target.
* *Reduced ongoing ingest throughput*: New file events and incremental scan updates process more slowly under sustained load.
* *Stalled scanning*: AI Data Engine components are configured for the size that you deploy. When the environment significantly exceeds that size, scanning can stall instead of only slowing down. To check for unhealthy workloads and resource constraints, refer to link:../administer/monitor-deployment-health.html[Monitor deployment health and investigate issues].
* *Storage capacity risk*: Undersized storage relative to total object count can push the metadata index toward capacity thresholds. Contact NetApp Support to plan a storage expansion.

Scale beyond the recommended size::
+
AI Data Engine components are configured for the size that you deploy, so adding vCPU, memory, or storage to the host VM doesn't automatically increase capacity. If the number of files or the performance that you need exceeds the size that you deployed, contact NetApp Support to readjust the sizing.
+
NOTE: A single-node deployment doesn't support high availability or horizontal scale-out. If your environment consistently exceeds 3 billion files, or you require high availability and fault tolerance, deploy an link:deploy-aide-multi-node.html[AIDE multi-node deployment] instead.

[[flexible-sizing-multi-node]]
=== Flexible sizing guidelines

<<multi-node-sizes,Small, Medium, and Large configurations>> are recommended baseline cluster configurations for a three to four day initial scan window, not hard capacity ceilings enforced by the software. Environments exceeding 6 billion files require custom sizing with NetApp.

What drives the sizing recommendations::
+
* *Total file and directory count*: Total object count is the dominant driver of storage and compute requirements. Larger environments require additional cluster nodes to distribute processing load and maintain performance.
* *High availability replication*: Multi-node deployments enable data replication across nodes by default for fault tolerance. Replication increases total storage and memory requirements compared to an equivalent single-node deployment.
* *Node count and workload distribution*: Processing throughput and total catalog capacity scale with the number of nodes in the cluster. Additional nodes distribute both the indexing workload and storage capacity across the cluster.
* *Required scan throughput*: Cluster-wide CPU and memory allocation governs the daily scan rate and how quickly the initial catalog completes.
* *Per-node storage performance*: High-performance storage is strongly recommended on each node, and total cluster capacity scales proportionally with node count.

What happens if you undersize or outgrow the deployed size::
+
Each configuration is tuned for a specific file count and scan rate. If your environment exceeds what the configuration supports, you can expect the following:
+
* *Extended initial catalog duration*: Fewer nodes or reduced per-node resources lower throughput, extending the initial catalog window proportionally.
* *Increased processing latency under peak load*: Insufficient memory across the cluster can cause elevated processing latency during high-volume ingestion periods.
* *Stalled scanning*: AI Data Engine components are configured for the size that you deploy. When the environment significantly exceeds that size, scanning can stall instead of only slowing down. To check for unhealthy workloads and resource constraints, refer to link:../administer/monitor-deployment-health.html[Monitor deployment health and investigate issues].
* *Storage capacity risk*: Insufficient cluster storage for the target object count can push the metadata index toward capacity thresholds. Contact NetApp Support to plan a storage expansion.

Scale beyond the recommended size::
+
Horizontal scaling of an existing multi-node cluster isn't supported. Adding worker nodes or dedicated storage nodes doesn't automatically increase scan processing, event ingestion, or catalog capacity. If your environment exceeds the size that you deployed, or you need more scan processing or event ingestion capacity, contact NetApp Support or your NetApp representative to plan the change.
+
NOTE: To scale beyond 10 billion files, contact your NetApp representative for node sizing guidance and custom scale.

[[kerberos-ad-requirements]]
== Kerberos and Active Directory requirements

Review these requirements before you scan SMB/CIFS shares with Kerberos authentication or map NFS user and group IDs to Active Directory names. The time synchronization, DNS, and host package requirements apply to Kerberos only. AI Data Engine (AIDE) is a Kerberos client: it authenticates to your existing Kerberos key distribution center (KDC) and doesn't act as a Kerberos server.

=== Time synchronization

Kerberos authentication fails when the clocks on the AIDE nodes and the KDC differ by more than the allowed clock skew. Active Directory allows a maximum difference of five minutes by default.

* Network Time Protocol (NTP) is active on all AIDE nodes.
* The AIDE nodes use a time source that is synchronized with your domain controllers.

=== DNS

* Every AIDE node can resolve the file server and the KDC by fully qualified domain name (FQDN).
* If you configure the nodes to use your Active Directory DNS server, that server must also resolve external names. Otherwise, AIDE can't reach the endpoints listed in <<outbound-internet-access,Outbound internet access>>.
* If you change the DNS settings on a multi-node deployment, configure your Active Directory DNS server as the only name server on every node. Name resolution in the cluster picks one of the listed name servers at random, so a name server that can't resolve Active Directory names causes intermittent failures.

To change the DNS settings, refer to "Fix name resolution" in link:../administer/configure-kerberos-smb-single-node.html#fix-name-resolution[Configure Kerberos for SMB/CIFS shares on a single-node deployment] or link:../administer/configure-kerberos-smb-multi-node.html#fix-name-resolution[Configure Kerberos for SMB/CIFS shares on a multi-node deployment].

=== Host packages

[cols="1,3",options="header"]
|===
|Deployment |Required packages

|Single node
|Kerberos client tools: `krb5-user` on Ubuntu or `krb5-workstation` on RHEL. The installer automatically installs `cifs-utils` to support Kerberos-authenticated SMB access.

|Multi-node
|`cifs-utils` on every node, and Kerberos client tools and an NFS client on the host where you create and test the keytab.

|===

`cifs-utils` is required on every AIDE node only for Kerberos-based SMB/CIFS scanning. The single-node installer installs it. On a multi-node deployment, you install it on every node. Kerberos scanning of an SMB/CIFS share fails if `cifs-utils` is missing on a node.

=== Active Directory attributes for NFS

To resolve NFS user and group IDs to Active Directory names, the `uidNumber` and `gidNumber` attributes must be populated, and replicated to the Global Catalog if AIDE queries it. Refer to link:../administer/configure-ad-nfs.html[Configure Active Directory identity mapping for NFS].
