= Configure a proxy for AI Data Engine
:icons: font
:imagesdir: ../media/

[.lead]
If your AI Data Engine host or cluster cannot reach the internet directly, configure a forward proxy so the installer and AI Data Engine can download components, pull container images, and register with NetApp Console. The proxy options are the same for single-node and multi-node deployments. The steps to prepare for and run the installation differ, so each deployment type has its own section.

== What goes through the proxy

Only internet-bound traffic uses the proxy. All AI Data Engine internet destinations use HTTPS on port 443, so your proxy must allow `CONNECT` to port 443 for each endpoint and host in <<proxy-allowlist,Hosts to allow on your proxy>>.

Traffic on your network connects directly and must stay reachable without the proxy:

* The Console agent (`--cm-host`)
* NFS, CIFS/SMB, ONTAP, and StorageGRID data sources
* Active Directory and LDAP
* The Kubernetes API server and the cluster's internal networks

== Supported proxy configurations

[cols="2,3,2",options="header"]
|===
|Configuration |Description |Authentication

|No proxy
|Direct connection to the internet; no proxy is used.
|None

|HTTP forward proxy
|AI Data Engine connects to the proxy over HTTP and tunnels HTTPS destinations with `CONNECT`.
|None, or HTTP Basic authentication (username and password)

|HTTPS forward proxy
|AI Data Engine connects to the proxy over TLS. If a private certificate authority (CA) signed the proxy certificate, you supply the CA certificate.
|None, or HTTP Basic authentication (username and password)

|===

You can address the proxy by hostname or IPv4 address.

IMPORTANT: AI Data Engine supports standard forward proxies that tunnel connections with HTTP `CONNECT`, including HTTPS destinations. Proxies that decrypt and re-sign HTTPS traffic with a custom certificate authority (TLS-inspecting proxies) are not supported. If your proxy inspects TLS traffic, exempt the endpoints and hosts in <<proxy-allowlist,Hosts to allow on your proxy>> from inspection, including the installer download host.

The following proxy features are not supported:

* NTLM, Kerberos, or client-certificate authentication to the proxy
* SOCKS proxies
* Proxy auto-configuration (PAC file or WPAD). Give the installer the proxy host and port directly.
* A different proxy for different destinations. One proxy carries all AI Data Engine internet traffic.
* An IPv6 address as the proxy address. Use a hostname instead; the hostname can resolve to IPv6.
* A proxy with an air-gapped installation. The installer rejects proxy options on an air-gapped installation.

The installer uses one proxy for every internet destination and every AI Data Engine component. The proxy settings are set during installation.

== Before you begin

* You have configured your proxy to allow the endpoints and hosts in <<proxy-allowlist,Hosts to allow on your proxy>>.
* You know the proxy host, port, and scheme (`http` or `https`). If the proxy requires authentication, you also know the username and password.
* If you use an HTTPS proxy with a privately signed certificate, you have the CA certificate as a PEM file, or a flat directory of `.crt` and `.pem` files, on the host where you run the installer.
* If your environment restricts internet access, you can download the installer through your proxy or transfer it from another machine. The command copied from NetApp Console downloads the installer without using the proxy.

== Proxy configuration parameters

[cols="2,1,3",options="header"]
|===
|Parameter |Default |Description

|`--proxy-host <host[:port]>`
|None
|Hostname or IPv4 address of the forward proxy, without `http://` or `https://`. Enables proxy configuration. Accepts an inline port (`host:port`). A port in `--proxy-host` takes precedence over `--proxy-port`.

|`--proxy-port <port>`
|`80` for HTTP, `443` for HTTPS
|Port the proxy listens on. Ignored if the port is already included in `--proxy-host`.

|`--proxy-scheme <http\|https>`
|`https`
|Protocol used to connect to the proxy server itself. This is not the scheme of the destinations that the proxy reaches. Most forward proxies listen on plain HTTP, so pass `--proxy-scheme http` for those.

|`--proxy-ca-cert <path>`
|None
|Path to a PEM file, or to a flat directory of `.crt` and `.pem` files, that contains the CA certificate that signed the proxy certificate. The installer reads a directory without recursing into subdirectories and merges the files into one bundle. Required for an HTTPS proxy whose certificate is signed by a private CA. Not used with an HTTP proxy.

|`--proxy-user <user>`
|None
|Username for basic authentication. With an HTTP proxy, the installer warns that credentials travel to the proxy unencrypted. Requires a password, supplied with `--proxy-password-file` or entered at the prompt.

|`--proxy-password-file <path>`
|None
|Path to a local file that contains only the proxy password, with permissions set to `0600` or `0400`. If you omit it, the installer prompts for the password with hidden input.

|`--proxy-type <r>`
|`r`
|Type of proxy. `r` is a regular forward proxy and is the default. Don't change it. TLS-inspecting proxies are not supported.

|`--proxy-bypass-registries <list>`
|None
|Single-node deployments only. Comma-separated list of container registries that the host reaches directly instead of through the proxy, for example an internal registry mirror. Accepts a host, `.domain`, `host:port`, IPv4 address, or CIDR. AWS hosts are rejected because AI Data Engine images must come from the NetApp container registry through the proxy.

|`--no-proxy`
|—
|Explicitly disables proxy configuration and skips proxy prompts. Use it only when the host has direct internet access.

|===

== Supply the proxy settings

You can supply the proxy settings in two ways when you run the install command copied from NetApp Console:

* *Interactive guided setup*: Run the install command in a terminal without proxy flags. The installer prompts you for the proxy settings. This is the default method.
* *Command-line flags*: Add the proxy flags to the install command. Use this method for automated or other non-interactive deployments that must run without prompts. The flags are optional. The installer prompts you for any proxy information you don't supply.

=== Interactive guided setup

When the installer runs in a terminal and you pass neither `--proxy-host` nor `--no-proxy`, it asks the following questions. If you pass a value as a parameter, the installer doesn't ask for it again.

// RESEARCH Confirm the prompt wording at release, including the proxy type prompt, and update the proxy type guidance if TLS inspection is qualified for GA.
[cols="2,3",options="header"]
|===
|Prompt |What to enter

|`Configure outbound proxy? (y/N)`
|Enter `y` if the host reaches the internet only through a proxy. The default is no.

|Proxy host or IP
|Enter the proxy hostname or IPv4 address, optionally with a port (`host:port`).

|Proxy scheme (`https` or `http`)
|Enter the protocol that your proxy listens on. The default is `https`.

|Proxy port
|Enter the proxy port. The default is `443` for HTTPS and `80` for HTTP.

|Proxy type
|Press Enter to accept the default, a regular forward proxy.

|CA certificate for the proxy's own certificate (HTTPS only, optional)
|Enter the path to the CA file or directory. Press Enter if a public CA signed the proxy certificate.

|Does the proxy require a username and password? (y/N)
|If yes, enter the username, and then enter the password twice. The installer doesn't echo the password.
|===

=== Command-line flags

If the copied install command includes `--no-proxy`, remove it when you add `--proxy-host`.

* If your proxy doesn't require authentication, omit `--proxy-user` and `--proxy-password-file`.
* If the proxy certificate is signed by a publicly trusted CA, or you use an HTTP proxy, omit `--proxy-ca-cert`.
* If you specify `--proxy-user` without `--proxy-password-file`, the installer prompts you for the password when you run it from a terminal.
* Without a terminal, the installer never prompts. Pass `--proxy-host` to use a proxy, and `--proxy-password-file` if the proxy needs a password. In a non-interactive run that is missing required proxy information, the installer stops before it makes any network connection.

CAUTION: With an HTTP proxy, the proxy username and password are sent in clear text. Use an HTTPS proxy when the proxy requires authentication.

== Configure the proxy for a single-node deployment

In a single-node deployment, AI Data Engine owns the VM that it installs on, so the installer configures every AI Data Engine part of the host for the proxy. The installer does the following:

* Downloads the k3s install script and binary through the proxy. It doesn't give k3s or the kubelet a system-wide proxy.
* Configures the k3s container runtime to pull images through the proxy. Registries that you list in `--proxy-bypass-registries` connect directly.
* Adds the CA certificate that you supply with `--proxy-ca-cert` to the host trust store.

You don't configure the VM container runtime or trust store. The operating system repositories on the VM must still provide the packages listed in link:single-node-prerequisites.html[AIDE single-node deployment prerequisites]. === Create a proxy password file

To supply the proxy password without being prompted for it, for example in an automated deployment, create a password file before you run the installer. The file contains only the password. Enter the password exactly as it is, without percent-encoding special characters.

Run the following commands as root. The single-node install command runs with `sudo`, so it can read a file under `/root`.

[source,bash]
----
umask 077
read -rs -p 'Proxy password: ' P && printf '%s' "$P" > /root/.aide-proxy-password; unset P; echo
chmod 600 /root/.aide-proxy-password
----

Delete the file after the installation completes.

The install command from NetApp Console downloads the installer from `d13jb5dapseb36.cloudfront.net` and starts it in one step. That download doesn't use the proxy. If the VM reaches the internet only through a proxy, the command stops at the download. In that case, download the installer yourself, and then run the install command from `sudo ./install-lite.sh` onward.

If the VM can reach `d13jb5dapseb36.cloudfront.net` directly, skip these steps. Run the command as copied, and add the proxy parameters inside the quotes, before the closing quote.

----

[[configure-proxy-multi-node]]
== Configure the proxy for a multi-node deployment

In a multi-node deployment, you own the Kubernetes cluster. The installer configures the AI Data Engine workloads for the proxy and doesn't change your nodes. Configure the container runtime and certificate trust on every node before you run the installer.

The installer checks the proxy from the installer host only. It doesn't check your nodes. If a node's container runtime isn't configured, the installation completes and pods on that node later show `ImagePullBackOff`.

=== Configure the container runtime proxy on every node

Use the same proxy host, port, and scheme that you give the installer. Configure every node, control plane and worker. The container runtime must reach the NetApp container registry host and the image layer bucket listed in link:aide-requirements.html#outbound-internet-access[Outbound internet access] through the proxy. Keep cluster-internal and node addresses in the no-proxy list.

If the proxy requires credentials, add `<user>:<encoded-password>@` after the scheme in the proxy URL, and percent-encode the username and password. For example, `@` is `%40`, `:` is `%3A`, a space is `%20`, `%` is `%25`, `#` is `%23`, and `?` is `%3F`. Because the file then contains the password, set its mode to `0600`.

// RESEARCH Confirm the proxy URL format for credentials in the runtime configuration. The source examples are masked. Also confirm the container runtime proxy procedures for OpenShift and AKS.
RKE2::
The `CONTAINERD_` prefix applies the proxy to image pulls only, not to RKE2 or the kubelet. Edit `/etc/default/rke2-server` on server nodes and `/etc/default/rke2-agent` on agent nodes:
+
[source,text]
----
CONTAINERD_HTTP_PROXY=http://proxy.example.com:3128
CONTAINERD_HTTPS_PROXY=http://proxy.example.com:3128
CONTAINERD_NO_PROXY=127.0.0.1,localhost,.svc,.cluster.local,<pod-cidr>,<service-cidr>,<node-subnet>
----
+
Restart the service. Use `rke2-agent` on agent nodes:
+
[source,bash]
----
sudo systemctl restart rke2-server
----

containerd managed by systemd (for example, kubeadm clusters)::
Create `/etc/systemd/system/containerd.service.d/http-proxy.conf`:
+
[source,ini]
----
[Service]
Environment="HTTP_PROXY=http://proxy.example.com:3128"
Environment="HTTPS_PROXY=http://proxy.example.com:3128"
Environment="NO_PROXY=127.0.0.1,localhost,.svc,.cluster.local,<pod-cidr>,<service-cidr>,<node-subnet>"
----
+
Then reload systemd and restart containerd:
+
[source,bash]
----
sudo systemctl daemon-reload && sudo systemctl restart containerd
----

Other distributions::
Follow the vendor's procedure for configuring an HTTP proxy for image pulls.

The `--proxy-bypass-registries` parameter isn't available for multi-node deployments. Configure registries that bypass the proxy in each node's container runtime.

=== Add the proxy CA certificate to every node

Do this step if you use an HTTPS proxy with a privately signed certificate. Install the same PEM file that you pass to `--proxy-ca-cert` into each node's trust store, and then restart the container runtime.

|Operating system |Commands

|Ubuntu
a|

----

|RHEL and Rocky Linux
a|
[source,bash]
----
sudo cp proxy-ca.pem /etc/pki/ca-trust/source/anchors/proxy-ca.crt && sudo update-ca-trust
----
|===

[[proxy-verification]]
== Proxy verification

Before the installer downloads anything, it runs a check from the installer host. The check confirms that the proxy responds, that the proxy accepts your credentials, and that the proxy certificate is valid for the scheme you chose. If the check fails, the installer stops and names the cause, for example a wrong port, a wrong scheme, or a rejected password (HTTP 407).

For multi-node deployments, the check covers the proxy only. It does not test whether the cluster nodes can reach the proxy.

== Troubleshoot proxy problems

If the proxy verification fails, the installer stops and reports an error. Use the following table to identify the cause of a verification error or a related problem during or after installation.

// RESEARCH Engineering to verify the installer error messages and the HTTP 407 behavior. Keep the CA certificate path row only if the installer behaves as described.
[cols="2,2,3",options="header"]
|===
|Symptom |Cause |Action

|The install command from NetApp Console stops at the download, with a `curl` timeout, a connection error, or an HTTP error.
|The VM or installer host can't reach `d13jb5dapseb36.cloudfront.net` directly. The download doesn't use the proxy.
|Download the installer as described for your deployment type. Check that the host is allowed on your proxy and exempt from TLS inspection.

|The installer stops at the proxy check with HTTP 407 or "Proxy Authentication Required".
|The proxy username or password is wrong, or the proxy requires a method other than basic authentication, or you didn't supply credentials.
|Check the username and the contents of the password file with your proxy administrator. Add `--proxy-user` and `--proxy-password-file` if the proxy requires authentication.

|The installer stops at the proxy check with a connection or TLS error.
|The port or scheme is wrong. An HTTP proxy fails with `--proxy-scheme https`, which is the default. For an HTTPS proxy with a private certificate, you didn't supply the CA certificate, or the CA certificate you supplied didn't sign the proxy certificate.
|Verify the host, port, and scheme. Pass `--proxy-scheme http` for an HTTP proxy. For an HTTPS proxy with a private certificate, supply the CA certificate that signed the proxy certificate with `--proxy-ca-cert`.

|The installer rejects the CA certificate path.
|The file is empty or isn't PEM-encoded, the directory is empty, or the path doesn't exist.
|Supply a valid PEM file, or a flat directory of `.crt` or `.pem` files.

|Downloads or AI Data Engine pods fail with HTTP 403 from the proxy.
|A host is missing from the proxy allowlist.
|Check the proxy access log for denied requests, and compare them with the endpoints and hosts in <<proxy-allowlist,Hosts to allow on your proxy>>.

|Pods stay in `ImagePullBackOff`.
|The NetApp container registry or the image layer bucket isn't allowed on the proxy, or a TLS-inspecting proxy re-signs those hosts. On a multi-node deployment, the container runtime on those nodes might not be configured for the proxy, or the nodes don't trust the proxy CA certificate. The installer doesn't check nodes, so the installation itself succeeds.
|Check the proxy allowlist and TLS inspection exemptions. On a multi-node deployment, check the container runtime proxy and CA certificate trust on every node first.
|===

The proxy settings are set during installation. The installer doesn't run again on an installed cluster. To change the proxy host, port, credentials, or CA certificate after installation, contact NetApp Support.
