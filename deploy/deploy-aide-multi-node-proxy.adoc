= Deploy AI Data Engine as a multi-node deployment with a proxy
:icons: font
:imagesdir: ../media/

[.lead]
Deploy AIDE as a multi-node deployment from NetApp Console when your Kubernetes cluster and the installer host reach the internet only through an outbound proxy. This topic includes every step of the multi-node deployment, along with the proxy steps. If your cluster and installer host have direct internet access, use link:deploy-aide-multi-node.html[Deploy AI Data Engine as a multi-node deployment] instead.

For the supported proxy types, the complete parameter reference, and the hosts to allow on your proxy, see link:configure-proxy.html[Learn about proxies for AI Data Engine].

== How the proxy applies to a multi-node deployment

In a multi-node deployment, you own the Kubernetes cluster. The installer configures the AI Data Engine workloads for the proxy and doesn't change your nodes. You must configure the container runtime and certificate trust on every node before you run the installer.

The installer checks the proxy from the installer host only. It doesn't check your nodes. If a node's container runtime isn't configured, the installation completes and pods on that node later show `ImagePullBackOff`.

The installer also doesn't install operating system packages on your nodes. Ensure that the nodes have the packages that your environment requires, and that your package managers have the appropriate proxy configuration if required in your environment.

.Before you begin

* You have _Organization admin_ or greater permissions in NetApp Console.
* Your Kubernetes cluster meets the multi-node prerequisites described in link:multi-node-prerequisites.html[AIDE multi-node deployment prerequisites] and link:aide-requirements.html[AIDE requirements].
* Sudo (or root) permissions are required on the machine from which you run the install command.
* An NFS server with an exported path is available and reachable from the cluster for the AIDE config volume.
* A NetApp Console agent https://docs.netapp.com/us-en/console-setup-admin/concept-agent-install-options.html#agent-console-deploy[is deployed^] and reachable from the cluster nodes. The Console Agent IP is required to run the install command.
* kubectl is available on the machine from which you run the install command, with cluster-admin access to the target cluster.
* The target Kubernetes namespace (default `aide`) already exists on the cluster before you run the install command.
* A configured StorageClass (default name: `aide-sc`) is available on the cluster and used for AIDE's stateful backing services.
* You have configured your proxy to allow the endpoints and hosts in link:configure-proxy.html#proxy-allowlist[Hosts to allow on your proxy].
* You know the proxy host, port, and scheme (`http` or `https`). If the proxy requires authentication, you also know the username and password.
* If you use an HTTPS proxy with a privately signed certificate, you have the CA certificate as a PEM file, or a flat directory of `.crt` and `.pem` files, on the installer host.

[[configure-proxy-multi-node]]
== Prepare every node

Complete these steps on every node, control plane and worker, before you run the installer.

=== Configure the container runtime proxy

Use the same proxy host, port, and scheme that you give the installer. The container runtime must reach the NetApp container registry host and the image layer bucket listed in link:aide-requirements.html#outbound-internet-access[Outbound internet access] through the proxy. Keep cluster-internal and node addresses in the no-proxy list.

If the proxy requires credentials, add `<user>:<encoded-password>@` after the scheme in the proxy URL, and percent-encode the username and password. For example, `@` is `%40`, `:` is `%3A`, a space is `%20`, `%` is `%25`, `#` is `%23`, and `?` is `%3F`. Because the file then contains the password, set its mode to `0600`.

// RESEARCH Confirm the proxy URL format for credentials in the runtime configuration. The source examples are masked. Also confirm the container runtime proxy procedures for OpenShift and AKS.
RKE2::
The `CONTAINERD_` prefix applies the proxy to image pulls only, not to RKE2 or the kubelet. Edit `/etc/default/rke2-server` on server nodes and `/etc/default/rke2-agent` on agent nodes:
+
[source,text]
----
CONTAINERD_HTTP_PROXY=http://proxy.example.com:3128
CONTAINERD_HTTPS_PROXY=http://proxy.example.com:3128
CONTAINERD_NO_PROXY=127.0.0.1,localhost,.svc,.cluster.local,<pod-cidr>,<service-cidr>,<node-subnet>
----
+
Restart the service. Use `rke2-agent` on agent nodes:
+
[source,bash]
----
sudo systemctl restart rke2-server
----

containerd managed by systemd (for example, kubeadm clusters)::
Create `/etc/systemd/system/containerd.service.d/http-proxy.conf`:
+
[source,ini]
----
[Service]
Environment="HTTP_PROXY=http://proxy.example.com:3128"
Environment="HTTPS_PROXY=http://proxy.example.com:3128"
Environment="NO_PROXY=127.0.0.1,localhost,.svc,.cluster.local,<pod-cidr>,<service-cidr>,<node-subnet>"
----
+
Then reload systemd and restart containerd:
+
[source,bash]
----
sudo systemctl daemon-reload && sudo systemctl restart containerd
----

Other distributions::
Follow the vendor's procedure for configuring an HTTP proxy for image pulls.

The `--proxy-bypass-registries` parameter isn't available for multi-node deployments. Configure registries that bypass the proxy in each node's container runtime.

=== Add the proxy CA certificate

Do this step if you use an HTTPS proxy with a privately signed certificate. Install the same PEM file that you pass to `--proxy-ca-cert` into each node's trust store, and then restart the container runtime.

[cols="1,3",options="header"]
|===
|Operating system |Commands

|Ubuntu
a|
[source,bash]
----
sudo cp proxy-ca.pem /usr/local/share/ca-certificates/proxy-ca.crt && sudo update-ca-certificates
----

|RHEL and Rocky Linux
a|
[source,bash]
----
sudo cp proxy-ca.pem /etc/pki/ca-trust/source/anchors/proxy-ca.crt && sudo update-ca-trust
----
|===

=== Check a node

Pull an AI Data Engine image on each node, using the registry credentials from NetApp Console. A successful pull confirms the runtime proxy, the allowlist, and the CA trust for that node.

// RESEARCH Confirm that customers can obtain the registry token for this command from NetApp Console, and the exact image name and tag to use.
[source,bash]
----
sudo crictl pull --creds "AWS:${AWS_ECR_TOKEN}" 582244788873.dkr.ecr.us-west-2.amazonaws.com/<image>:<tag>
----

== Copy the install command

. In NetApp Console, navigate to *AI data hub* > *AI Data Engine*.
+
The AI Data Engine landing page appears.

. Select *Deploy AI Data Engine*.
. Select the *Multi-node* deployment option and select *Next*.
. Select your configuration size:
+
* *Small*: recommended for environments with up to approximately 1 billion files.
* *Medium (Default)*: recommended for environments with up to approximately 3 billion files.
* *Large*: recommended for environments with up to approximately 6 billion files.
+
These sizes are recommended baselines, not hard limits. An AIDE multi-node deployment requires custom sizing with NetApp for environments beyond 6 billion files; see link:aide-requirements.html#flexible-sizing-multi-node[flexible sizing guidelines] for details.
+
The wizard generates the install command with the configuration size you select. You don't need to edit the command to set the size.

. Copy the install command displayed in the wizard to an editor.

The install command downloads the installer from `d13jb5dapseb36.cloudfront.net` and starts it in one step. That download doesn't use the proxy.

* If the installer host can reach `d13jb5dapseb36.cloudfront.net` directly, skip the next section and continue with <<create-password-file-multi-node,Create a proxy password file>>. Run the install command as copied. If you add proxy parameters, add them inside the quotes, before the closing quote.
* If the installer host reaches the internet only through a proxy, the command stops at the download. Complete the next section first. Only the installer host needs this. Your nodes don't download the installer.

[[download-installer-multi-node]]
== Download the installer through the proxy

Download the installer yourself, and then run the install command from `./install-enterprise.sh` onward.

. Get the installer onto the installer host. Use any method that your environment allows, and then place the file on the installer host.
+
To download the installer from the installer host through your proxy:
+
[source,bash]
----
mkdir -p ~/aide && cd ~/aide
curl -fsSL -x http://PROXY_HOST:PROXY_PORT \
  https://d13jb5dapseb36.cloudfront.net/aide/latest/aide-installer.tar.gz -o aide-installer.tar.gz
----
+
If the proxy requires a username, add `--proxy-user USER` to the `curl` command. If you omit the password, `curl` prompts for it, so it isn't saved in your shell history.
+
* Use `https://` in the `-x` address if your proxy listens on HTTPS.
* If your proxy uses a privately signed certificate, add `--proxy-cacert CA_FILE`, or add the CA certificate to the installer host trust store first.
* With an HTTPS proxy and a `curl` version earlier than 8.3, which includes Ubuntu 22.04, the download can pause for about a minute. Wait for it to finish.
+
Alternatively, download `\https://d13jb5dapseb36.cloudfront.net/aide/latest/aide-installer.tar.gz` from another computer, and then copy it to the installer host with `scp` or your usual file transfer method.

. Extract the installer, and change to the installer folder:
+
[source,bash]
----
tar -xzf aide-installer.tar.gz
cd installer
----
+
Run every following command from inside this installer folder. The `version.txt` file in the folder shows the installer build version.

. Prepare the install command that you copied from NetApp Console. It downloads the installer and then runs `./install-enterprise.sh` with your parameters. Because you already downloaded the installer:
+
* Delete everything before `./install-enterprise.sh`, so the command starts with `./install-enterprise.sh`. If the command runs it as `sudo ./install-enterprise.sh`, keep the `sudo`.
* If the command was wrapped in quotes, for example `bash -c '...'`, delete the single quote (`'`) at the very end.
* If the command contains `--no-proxy`, delete it.
+
The remaining command looks like this after you add the proxy parameters:
+
[source,bash]
----
./install-enterprise.sh --flavor <small|medium|large> --kubeconfig <kubeconfig-path> --nfs-server <nfs-server> --nfs-data-share <export-path> --registry <registry> --account-id <account-id> --organization-id <organization-id> --agent-id <agent-id> --cm-host <console-agent-ip> --proxy-host proxy.example.com --proxy-port 3128 --proxy-scheme http
----

[[create-password-file-multi-node]]
== Create a proxy password file

If your proxy requires authentication and you want to supply the password without being prompted for it, for example in an automated deployment, create a password file before you run the installer. Otherwise, skip this section. The installer prompts for the password with hidden input.

The file contains only the password. Enter the password exactly as it is, without percent-encoding special characters.

Create the file as the same user who runs `./install-enterprise.sh`, because the installer reads the file as that user. The multi-node install command typically doesn't run with `sudo`, so a file under `/root`, which only root can read, stops the installation.

[source,bash]
----
umask 077
read -rs -p 'Proxy password: ' P && printf '%s' "$P" > $HOME/.aide-proxy-password; unset P; echo
chmod 600 $HOME/.aide-proxy-password
----

Delete the file after the installation completes.

== Supply the proxy settings

You can supply the proxy settings in two ways:

* *Interactive guided setup*: The installer prompts you for the proxy settings. This is the default method.
* *Command-line flags*: Add the proxy parameters to the install command. The flags are optional. Use them for automated or other non-interactive deployments that must run without prompts. The installer prompts you for any proxy information you don't supply.

Use the same proxy host, port, scheme, and CA certificate that you configured on the nodes.

[[interactive-setup-multi-node]]
=== Interactive guided setup

When you run the install command in a terminal without `--proxy-host` or `--no-proxy`, the installer asks the following questions. If you pass a value as a parameter, the installer doesn't ask for it again.

// RESEARCH Confirm the prompt wording at release, including the proxy type prompt, and update the proxy type guidance if TLS inspection is qualified for GA.

[cols="2,3",options="header"]
|===
|Prompt |What to enter

|`Configure outbound proxy? (y/N)`
|Enter `y`.

|Proxy host or IP
|Enter the proxy hostname or IPv4 address, optionally with a port (`host:port`).

|Proxy scheme (`https` or `http`)
|Enter the protocol that your proxy listens on. The default is `https`.

|Proxy port
|Enter the proxy port. The default is `443` for HTTPS and `80` for HTTP.

|Proxy type
|Press Enter to accept the default.

|CA certificate for the proxy's own certificate (HTTPS only, optional)
|Enter the path to the CA file or directory. Press Enter if a public CA signed the proxy certificate.

|Does the proxy require a username and password? (y/N)
|If yes, enter the username, and then enter the password twice. The installer doesn't echo the password.
|===

Without a terminal, the installer never prompts. Pass `--proxy-host` to use a proxy, and `--proxy-password-file` if the proxy needs a password.

[[command-line-flags-multi-node]]
=== Command-line flags

Add the proxy parameters to the install command after the last existing parameter.

* If you run the install command as copied from NetApp Console, add the parameters inside the quotes, before the closing quote.
* If you downloaded the installer and shortened the command, add the parameters to the end of the shortened command.

If the command contains `--no-proxy`, remove it. Keep every other parameter from the install command. For the description and default of each parameter, see link:configure-proxy.html#proxy-parameters[Proxy configuration parameters]. The following examples show only the proxy parameters.

.HTTP proxy with a username and password
[source,bash]
----
--proxy-host proxy.example.com \
--proxy-port 3128 \
--proxy-scheme http \
--proxy-user svc-aide \
--proxy-password-file $HOME/.aide-proxy-password
----

.HTTPS proxy with a privately signed certificate and no authentication
[source,bash]
----
--proxy-host proxy.example.com \
--proxy-port 8443 \
--proxy-scheme https \
--proxy-ca-cert $HOME/proxy-ca.pem
----

* If your proxy doesn't require authentication, omit `--proxy-user` and `--proxy-password-file`.
* If you specify `--proxy-user` without `--proxy-password-file`, the installer prompts you for the password when you run it from a terminal.

CAUTION: With an HTTP proxy, the proxy username and password are sent in clear text. Use an HTTPS proxy when the proxy requires authentication.

== Run the installation

. Run the install command from your target host with kubectl access to your Kubernetes cluster. If you downloaded the installer, run the command from the installer folder.
+
Before the installer downloads anything, it checks from the installer host that the proxy responds, that the proxy accepts your credentials, and that the proxy certificate is valid for the scheme you chose. If the check fails, the installer stops and names the cause. See <<troubleshoot-multi-node,Troubleshoot proxy problems>>. The check doesn't test whether the cluster nodes can reach the proxy.
+
NOTE: The `sudo` command removes environment variables, so always pass `--kubeconfig` explicitly if you run the installer with `sudo`. For more information, see link:multi-node-prerequisites.html[AIDE multi-node deployment prerequisites].
+
NOTE: Installation takes about 30 minutes to complete. Timeouts and retries might occur, and this is normal.

. If you didn't pass all of the proxy parameters, answer the proxy prompts. See <<interactive-setup-multi-node,Interactive guided setup>>.
. When prompted, confirm the host IP address and user ID to continue the installation.
. Monitor the progress screen until the success screen appears and displays "AI Data Engine deployed".

.Result
Your AI Data Engine multi-node deployment is deployed and connected to NetApp Console. You can now link:../data-sources/connect-data-source.html[connect a data source] to start scanning.

[[check-proxy-multi-node]]
== Check the proxy after installation

The AI Data Engine operator logs the proxy that it uses. The log never includes the password. To check the proxy, run the following command from a host with kubectl access to your cluster:

[source,bash]
----
kubectl -n aide logs -l control-plane=controller-manager -c chart-fetcher | grep -m1 'proxy enabled'
----

The line shows the proxy endpoint, whether authentication is on, and whether a CA certificate is mounted.

[[troubleshoot-multi-node]]
== Troubleshoot proxy problems

If the proxy check fails, the installer stops and names the cause.

// RESEARCH Engineering to verify the installer error messages and the HTTP 407 behavior. Keep the CA certificate path row only if the installer behaves as described.
[cols="2,2,3",options="header"]
|===
|Symptom |Cause |Action

|The install command from NetApp Console stops at the download, with a `curl` timeout, a connection error, or an HTTP error.
|The installer host can't reach `d13jb5dapseb36.cloudfront.net` directly. The download doesn't use the proxy.
|Follow <<download-installer-multi-node,Download the installer through the proxy>>. Check that the host is allowed on your proxy and exempt from TLS inspection.

|The installer stops at the proxy check with HTTP 407 or "Proxy Authentication Required".
|The proxy username or password is wrong, the proxy requires a method other than basic authentication, or you didn't supply credentials.
|Check the username and the contents of the password file with your proxy administrator. Add `--proxy-user` and `--proxy-password-file` if the proxy requires authentication.

|The installer stops at the proxy check with a connection or TLS error.
|The port or scheme is wrong. An HTTP proxy fails with `--proxy-scheme https`, which is the default. For an HTTPS proxy with a private certificate, you didn't supply the CA certificate, or the CA certificate you supplied didn't sign the proxy certificate.
|Verify the host, port, and scheme. Pass `--proxy-scheme http` for an HTTP proxy. For an HTTPS proxy with a private certificate, supply the CA certificate that signed the proxy certificate with `--proxy-ca-cert`.

|The installer rejects the CA certificate path.
|The file is empty or isn't PEM-encoded, the directory is empty, or the path doesn't exist.
|Supply a valid PEM file, or a flat directory of `.crt` or `.pem` files.

|The installer stops because it can't read the password file.
|You created the password file as a different user than the one who runs the installer, for example under `/root`.
|Create the file as the user who runs the installer.

|Downloads or AI Data Engine pods fail with HTTP 403 from the proxy.
|A host is missing from the proxy allowlist.
|Check the proxy access log for denied requests, and compare them with the endpoints and hosts in link:configure-proxy.html#proxy-allowlist[Hosts to allow on your proxy].

|Pods stay in `ImagePullBackOff` on some or all nodes.
|The container runtime on those nodes isn't configured for the proxy, or the nodes don't trust the proxy CA certificate. The installer doesn't check nodes, so the installation itself succeeds. The NetApp container registry or the image layer bucket might also not be allowed on the proxy.
|Check the container runtime proxy and CA certificate trust on the nodes first, and then check the proxy allowlist and TLS inspection exemptions. Use <<check-node-multi-node,Check a node>> to confirm each node.
|===
